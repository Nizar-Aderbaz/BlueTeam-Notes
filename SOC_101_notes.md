# Email Forensics

## Message-ID

A unique ID generated by the **originating mail server or client**.

Format: `someid@domain.com`

Used to trace emails, detect duplicates, or identify mass spam.

```
Message-ID: CA+2abcD=3@mail.evilserver.ru
```

> Often matches the sender's domain. A mismatch is a **weak signal**, not proof of anything on its own.

---

## From

The sender name and email shown to the user. **Can be spoofed easily.**

```
From: Microsoft Support <support@microsoft.com>
```

> Don't trust it blindly — compare it with `Return-Path` and the `Authentication-Results` header.

---

## Return-Path

The **envelope sender** (SMTP `MAIL FROM`) used for bounce messages. Often reveals the real sending infrastructure, but **it can also be forged**.

```
Return-Path: scammer@hackedsite.ru
```

> A difference from `From` is a red flag **only together with other signs** — mailing lists and bulk-mail services legitimately use a different Return-Path.

---

## Reply-To

The address where your reply will go. Attackers may redirect replies to a fake address.

```
Reply-To: scammer@gmail.com
```

> If it's different from `From`, be cautious.

---

## Received

Shows the **path the email took** across mail servers. Read from **bottom to top**. Important for finding the source IP address.

```
Received: from hackerhost.ru (123.45.67.89)
```

> Only trust the hops added by **your own** (or your provider's) servers — earlier hops can be forged by the sender.

**IP lookup tools:**
- https://ipinfo.io
- https://whatismyipaddress.com
- https://www.abuseipdb.com

**Look for:**
- Unusual country of origin
- Unknown server names
- Private/internal IPs where an external one is expected

---

## Authentication-Results

Shows whether the sender passed email verification protocols: **SPF**, **DKIM**, **DMARC**.

```
Authentication-Results: spf=fail dkim=fail dmarc=fail
```

### SPF (Sender Policy Framework)
Checks whether the sending IP is **authorized** to send for the domain in the **envelope sender (Return-Path / MAIL FROM)** — *not* the `From` header. `SPF = fail` → the sender may be spoofing.

### DKIM (DomainKeys Identified Mail)
Uses a **cryptographic signature** (tied to the signing domain, `d=`) to verify the message wasn't tampered with. `DKIM = fail` → the email may be fake or altered.

### DMARC (Domain-based Message Authentication, Reporting and Conformance)
Ties SPF and DKIM to the **`From` domain**. DMARC passes if **SPF *or* DKIM passes *and is aligned*** with the `From` domain. If it fails, the domain owner's policy (`p=none` / `quarantine` / `reject`) tells the receiver what to do.

> ⚠️ Passing SPF/DKIM/DMARC does **not** mean an email is safe. Attackers can register lookalike domains with valid authentication, or send from compromised legitimate accounts.

## Phishing Detection — Red Flags

| Field | Normal ✅ | Suspicious 🚨 |
|---|---|---|
| From | Matches the legit domain | Free-mail domain posing as a company, or typo domain (e.g., `paypa1.com`) |
| Return-Path | Same domain as From (or a known mail provider) | Unknown or unrelated domain |
| Reply-To | Same as From | Goes to a different / attacker address |
| SPF / DKIM / DMARC | All pass and align with From | One or more fail |
| Received | Known IPs / servers | Unknown IP, unexpected country |
| Message-ID | Ends with a legit domain | Strange or random domain |
| Links | Point to the real domain | Shortened or lookalike URLs |
| Attachments | Expected business files (still verify!) | `.exe`, `.html`, `.js`, `.scr`, `.hta`, `.vbs`, `.lnk`, `.iso`, `.docm`, `.xlsm`, password-protected `.zip` |

> PDFs and Office documents can be malicious too — context matters (was it expected? from whom?).

# Network Analysis Methodology

## Wireshark

**Step 1 — Set timestamps to UTC:**
```
View → Time Display Format → UTC Date and Time of Day (1970-01-01 01:02:03.123456)
```

**Step 2 — Get a big picture:**
`Statistics → Capture File Properties` → check number of packets and duration between first and last packet.

**Step 3 — Find the most communicating IPs:**
`Statistics → Conversations` (and `Endpoints`) → the most-talking IP may be the victim or the attacker.

**Step 4 — Check protocol distribution:**
`Statistics → Protocol Hierarchy` → identify the most-used protocols.

### Useful Wireshark Filters

| Filter | What it shows |
|---|---|
| `http` | HTTP traffic |
| `arp` | ARP traffic (look for floods / scanning) |
| `smtp` | SMTP email communication |
| `smb` or `smb2` | SMB shares |
| `tcp.flags.syn==1 && tcp.flags.ack==0` | SYN scan (port scanning) |
| `dns` / `dns.qry.name` | DNS queries |
| `tls.handshake.extensions_server_name` | SNI — the server name requested in TLS |
| `icmp.type == 8` | Ping (echo request) scan |
| `tls.handshake.type == 1` | TLS Client Hello |
| `tls.handshake.type == 2` | TLS Server Hello |
| `tls.record.version` | TLS version |
| `kerberos` | Kerberos authentication traffic |
| `ldap.AttributeDescription == "givenName"` | LDAP user enumeration |
| `nbns` | NetBIOS name resolution |

# IDS / IPS

| Type | Description |
|---|---|
| **IDS** (Intrusion Detection System) | Passive monitoring and analysis; generates alerts and logs |
| **IPS** (Intrusion Prevention System) | Inline traffic inspection; blocks/drops packets via predefined rules; terminates connections; generates alerts and logs |
| **NIDS/NIPS** (Network-Based) | Operates at the network level; analyzes traffic through network appliances |
| **HIDS/HIPS** (Host-Based) | Operates at the endpoint level; analyzes activities on the host (file system, logins, apps) |

## Detection Methods

| Method | Description |
|---|---|
| **Signature-Based** | Compares traffic/activities against known attack patterns; cannot detect unknown threats |
| **Behavior-Based** | Detects anomalies deviating from a baseline; more effective for unknown threats; higher false-positive rate |
| **Rule-Based** | Enforces policies defining acceptable actions or violations; highly customizable; requires frequent maintenance |

# Snort

An open-source IDS/IPS from Cisco.

> The commands and rules below use **Snort 2.x** syntax (`snort.conf`). Snort 3 uses `snort.lua` and different options.

## Operating Modes

| Mode | Description |
|---|---|
| **Sniffer Mode** | Reads network packets and displays them in the console |
| **Packet Logger Mode** | Logs packets to disk files for offline analysis |
| **IDS/IPS Mode** | Monitors network traffic against defined rules |

## Key Libraries

| Library | Purpose |
|---|---|
| `libpcap` | Gives Snort the capability to capture packets |
| `PCRE` | Enables pattern matching and regular expressions within rules |
| `ZLIB` | Handles compression and decompression |

## Promiscuous Mode

A network interface configuration where the NIC captures **all packets on the network segment**, regardless of destination address (normally a NIC only processes packets addressed to it).

```bash
sudo ip link set eth0 promisc on
```

## Configuration

- Main config file: `/etc/snort/snort.conf` — defines all settings, components, and variables
- Rules folder: `/etc/snort/rules/` — contains all predefined rule files
- `HOME_NET` — the network range(s) (IP/CIDR) Snort treats as the protected/internal network; set in `snort.conf`

```bash
snort -T -c /etc/snort/snort.conf          # test config file
snort -i lo -e -d                          # dump link-layer headers (-e) and packet data (-d)
snort -i lo -e -d -l /home/user/logs       # log packets for later analysis
```

## Rule Syntax

```
alert icmp any any -> 8.8.8.8 any (msg:"ICMP traffic to 8.8.8.8 detected"; sid:1000001; rev:1;)
^---------- rule header ---------^ ^---------------- rule options ----------------------^
```

| Field | Options |
|---|---|
| **Actions** | `alert`, `log`, `pass`, `drop`, `reject`, `sdrop` |
| **Protocols** | `ip`, `tcp`, `udp`, `icmp` |
| **Direction** | `->` (source to dest), `<>` (bidirectional) |
| **SID** | Unique rule identifier — local rules start from `1000001`; **every rule needs its own SID** |
| **REV** | Revision number — increment by 1 on every change |

## Running Snort

```bash
# Run and test alert rules (IDS mode)
snort -A console -l /tmp/logs/ -i lo -c /etc/snort/snort.conf -q

# Run against a PCAP file
snort -c /etc/snort/snort.conf -q -r file.pcap -A console

# Run in fast alert mode
snort -A fast ...
```

## Snort as IPS (Inline Mode)

Requires **two network interfaces** (Snort bridges them). Uses the `afpacket` DAQ for real-time packet dropping.

```bash
snort -q -A console -i eth0:eth1 -c /etc/snort/snort.conf --daq afpacket -Q
```

> Use **Snorpy** to help build rules via a GUI.

## Example Rules

> These all use `alert`. In **inline (IPS) mode**, change `alert` to `drop` to actually block the traffic.

**Detect `.exe` downloads over HTTP (by Content-Type):**
```
alert tcp any 80 -> any any (
    msg:"Potential .exe file download over HTTP";
    flow:to_client,established;
    content:"Content-Type: application/x-msdownload"; http_header;
    sid:1000001; rev:1;
)
```

**Detect MZ/PE signature even when the extension is spoofed:**
```
alert tcp any 80 -> any any (
    msg:"HTTP payload contains DOS MZ executable signature";
    flow:to_client,established;
    file_data;
    content:"|4D 5A|"; depth:2;
    sid:1000002; rev:1;
)
```
> `depth:2` → Snort only looks at the first 2 bytes of the payload.

**Detect SSLoad activity by User-Agent (example):**
```
alert tcp any any -> any any (
    msg:"Possible SSLoad activity via User-Agent";
    flow:to_server,established;
    content:"User-Agent: SSLoad/1.1"; http_header; nocase;
    sid:1000003; rev:1;
)
```
> Take indicators like this from a published threat report and verify them. A static User-Agent is easy for attackers to change, and this rule does **not** detect Cobalt Strike.

**Detect SSH brute force (many new connections):**
```
alert tcp any any -> any 22 (
    msg:"Possible SSH brute force";
    flags:S;
    detection_filter:track by_src, count 5, seconds 30;
    sid:1000004; rev:1;
)
```
> `flags:S` matches only new connections (SYN). Without it, every packet of a normal SSH session would count toward the threshold and cause false positives.

# Endpoint Security

**Endpoint** = any device connected to the organization's network.

| Tool | Description |
|---|---|
| **EDR** (Endpoint Detection & Response) | Monitors and responds in real time; requires an agent deployed on every endpoint; monitors processes, files, registry, and network activity |
| **XDR** (Extended Detection & Response) | Integrates multiple security controls and telemetry; automated response to routine threats |
| **DLP** (Data Loss Prevention) | Protects sensitive data at rest, in transit, and in use |
| **UEBA** (User and Entity Behavior Analytics) | Monitors user/entity behavior patterns; detects deviations from baseline (insider threats, account compromise, data exfiltration) |
| **HIDS/HIPS** | Host-based intrusion detection/prevention |
| **Host-based Firewall** | Controls incoming and outgoing traffic on a single host |

## Endpoint Security Monitoring Areas

| Area | What to Monitor |
|---|---|
| **Process Execution** | Running processes, executable files, PIDs, command-line arguments, parent-child hierarchy |
| **File System Changes** | Creation, modification, deletion; File Integrity Monitoring (FIM) |
| **Network Connections** | Traffic initiated from the endpoint; associated processes and executables |
| **Registry Modifications** | Registry keys and values; detect backdoors, persistence, and detection evasion |

# Windows Network Analysis

> Attackers may create open shares on a compromised system to store tools for lateral movement or to stage data archives for exfiltration (often in password-protected ZIPs).

```cmd
:: View shared resources on a (remote or local) host
net view \\127.0.0.1

:: Create a share
net share Share=C:\Users\Public\share

:: List shares on THIS computer
net share

:: List incoming sessions to this machine (who is connected to us)
net session

:: List outgoing connections / shares THIS machine has mapped on other systems
net use

:: See all connections + associated processes
netstat -bano
:: a = all connections/listening ports | n = numeric (no DNS) | o = include PID | b = executable name (needs admin)
```

> Alternatively, use **TCPView** (Sysinternals) for a GUI view of all connections.

# Windows Process Analysis

## Process Types

| Type | Examples |
|---|---|
| OS Core | `system`, `smss.exe`, `csrss.exe` |
| User (Application) | `chrome.exe`, `notepad.exe` |
| Service (Background) | Windows Update, Print Spooler, `lsass.exe` |

## Key Commands

```cmd
tasklist                              :: list all processes and binaries
tasklist /V                           :: verbose mode (includes running user)
tasklist /M                           :: list all DLLs (modules) associated with each process
tasklist /FI "PID eq 8292"            :: check if a specific PID is still running
tasklist /FI "IMAGENAME eq payload.exe" /M

wmic process where processid=8292 get name, parentprocessid, processid
wmic process get name, processid, parentprocessid | find "1276"   :: find siblings of a parent
wmic process where processid=3004 get commandline                  :: see full command line
```

> ⚠️ `wmic` is **deprecated** and not installed by default on newer Windows 11 builds. PowerShell equivalent:

```powershell
Get-CimInstance Win32_Process |
  Select-Object Name, ProcessId, ParentProcessId, CommandLine
```

> `netstat` → `tasklist` → `wmic` (or `Get-CimInstance`) is a solid process investigation chain.
> If a PowerShell payload compromised the endpoint, the full command line shows the payload.

### `smss.exe` — Session Manager Subsystem
Initiates and manages user sessions. Spawns `wininit.exe` and `csrss.exe` (and `winlogon.exe` for user sessions).

| Property | Value |
|---|---|
| Image Path | `%SystemRoot%\System32\smss.exe` |
| Parent Process | System (PID 4) |
| Instances | 1 master + 1 child per session (children exit after setting up the session) |
| User Account | Local System |
| Start Time | Within seconds of boot |

---

### `csrss.exe` — Client/Server Runtime Subsystem
Manages console windows, imports DLLs for Windows API, handles GUI shutdown tasks.

| Property | Value |
|---|---|
| Image Path | `%SystemRoot%\System32\csrss.exe` |
| Parent Process | `smss.exe` (appears as orphan) |
| Instances | 2 or more |
| User Account | Local System |
| Start Time | Within seconds of boot |

---

Initializes the system; spawns `services.exe` and `lsass.exe`.

| Property | Value |
|---|---|

| Instances | 1 |
| User Account | Local System |
| Start Time | Within seconds of boot |

### `services.exe` — Service Control Manager
Starts, stops, and interacts with Windows services. Sets the `LastKnownGood` registry value.

| Property | Value |
|---|---|

# Windows Registry

A hierarchical database of hives, keys, subkeys and values that stores system configuration for the OS and installed components.

| Hive | Description |
|---|---|
| **HKCR** (HKEY_CLASSES_ROOT) | Registered apps, file associations, ProgIDs, COM objects |
| **HKCU** (HKEY_CURRENT_USER) | Settings of the **currently logged-in user** (a link to that user's key under `HKU`) |
| **HKLM** (HKEY_LOCAL_MACHINE) | Settings that apply to **all users**: hardware, software, drivers, security, services |
| **HKU** (HKEY_USERS) | Settings for **all loaded user profiles**, keyed by SID |
| **HKCC** (HKEY_CURRENT_CONFIG) | Current hardware profile (a link to part of `HKLM\SYSTEM`) |

## Persistence Locations (Threat Actor Favorites)

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run          ← current user
HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce
HKLM\Software\Microsoft\Windows\CurrentVersion\Run          ← all users
HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce
HKLM\SYSTEM\CurrentControlSet\Services                      ← all installed services
```

> Also check: Startup folders, `Winlogon` (`Userinit` / `Shell`) values, scheduled tasks, and WMI event subscriptions.

## Querying Registry Keys



## /proc Virtual Filesystem

`/proc` is a virtual filesystem providing an interface to the kernel. The numbered folders inside are **Process IDs**.

| File inside `/proc/<PID>/` | Contents |
|---|---|
| `cmdline` | Command-line arguments used to invoke the process |
| `cwd` | Symlink to the process's current working directory |
| `exe` | Symlink to the process's binary (shows `(deleted)` if the file was removed) |
| `environ` | Environment variables of the process |
| `fd/` | Open file descriptors (files, sockets) |
| `maps` | Memory mappings (loaded libraries, injected regions) |
| `status` | Name, state, PID/PPID, UID, memory info |

# Linux CronJobs

CronJobs are like Scheduled Tasks in Windows — used for repetitive automated tasks.

```bash
crontab -e                                       # edit your own crontab
*/1 * * * * python3 /home/user/program.py        # example entry: runs every 1 minute

crontab -l                                       # list your own cronjobs
crontab -u root -l                               # list cronjobs of root (needs root)
```

**Where cronjobs live:**

| Location | Contents |
|---|---|
| `/etc/crontab`, `/etc/cron.d/` | System-wide cronjobs |
| `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/`, `/etc/cron.monthly/` | System-wide scheduled scripts |
| `/var/spool/cron/crontabs/` (Debian/Ubuntu) or `/var/spool/cron/` (RHEL/CentOS) | **Per-user** crontabs for all users (needs root) |

> Investigate files inside `/etc/cron.daily`, `/etc/cron.weekly`, etc. using `strings`, `cat`, or by hashing them.

# SIEM

**Security Information and Event Management** — a technology for:
- Log Management
- Real-time Monitoring
- Alerting and Notification
- Incident Response
- Dashboards, Reports, Visualization
- Threat Intelligence Integration

## SIEM Components (Splunk-style architecture)

```
Endpoint (Data Source)
    ↓
Forwarder (agent installed on endpoint — sends data)
    ↓
Indexer (data processing + storage)
    ↓
Search Head (handles search and visualization)
    ↓
Analyst (investigates and analyzes)
```

## SIEM Deployment Models

| Model | Description |
|---|---|
| **Single Instance** | All components on one machine — ideal for learning and small setups |
| **Distributed** | Multiple servers each serving a specific role (indexing, search, data collection) — good for scalability |
| **Clustered** | Multiple servers performing the **same** role for redundancy — best for high availability |

## Linux Log Analysis (CLI)

```bash
awk '{print $1, $3}' log.txt                                          # extract specific fields
grep -E 'error|warning' log.txt                                       # filter by keyword
grep -Ei '%3C|%3E|<|>' access.log                                     # detect XSS attempts
grep -Ei '\.\./|%2e%2e%2f|%2e%2e/|\.\.%2f' access.log                 # detect path traversal attempts
```

> Start by extracting all IPs with `cut`, look for rogue IPs or high connection counts, then examine suspicious User-Agent strings.

# Splunk (SPL)

## Basics

- `index=web_logs` — search all events in an index
- `index=web_logs error` — keyword filter
- `index=web_logs status=500` — filter by field value
- `index=web_logs earliest=-15m` — last 15 minutes
- `index=web_logs earliest="07/25/2025:09:00:00" latest="07/25/2025:12:00:00"` — fixed time range
- `index=web_logs | stats count` — total event count
- `index=web_logs | stats count by status` — count by field (e.g., HTTP status)
- `index=web_logs | stats count by clientip` — count by client IP
- `index=web_logs | stats avg(response_time)` — average response time
- `index=web_logs | where response_time > 2` — complex condition
- `index=web_logs | top 5 uri_path` — top 5 requested URLs
- `index=web_logs | timechart count span=1m` — events per minute (visualization)
- `index=web_logs | timechart avg(response_time)` — average response time over time
- `index=web_logs | table _time, status, uri_path, response_time` — select specific fields
- `index=web_logs | rename uri_path as URL` — rename a field
- `index=web_logs | dedup clientip | table clientip, status, useragent` — one row per unique client IP

## User-Agents, Geo, Metadata

```spl
index="index_access" | top limit=5 useragent
```
Top 5 User-Agents.

Filter by User-Agent.

```spl
index="index_access" | iplocation clientip | geostats count by Country
```

Geomap by country.

Show all sourcetypes.

## Extracting Values with `rex` (e.g., analyzing brute-force attempts)

# Threat Intelligence

**Actionable knowledge about cyber threats** — collected, analyzed, and processed to guide security decisions.

Includes: who might attack (actors, groups), why (motives, objectives), how (TTPs), and what to look for (IOCs).

## Types of Threat Intelligence

| Type | Focus |
|---|---|
| **Strategic** | High-level trends, risks, impacts; actor motives and capabilities — guides long-term security strategy |
| **Tactical** | TTPs — how threat actors operate and behave |
| **Operational** | Imminent threats, plans, timelines — specific campaigns and the actors behind them |
| **Technical** | Tools, infrastructure, technical capabilities; IOCs — integrated into tooling to enhance detection |

## The Intelligence Cycle

1. **Planning and Direction (Requirements)** — what intelligence is needed, who needs it, and why
2. **Collection** — gathering raw data
3. **Processing** — normalizing and organizing the raw data so it can be analyzed
4. **Analysis** — turning raw, incomplete, or overwhelming data into meaningful, actionable intelligence
5. **Dissemination** — delivering processed intelligence reports and alerts to decision-makers
6. **Feedback** — consumers provide input on the intelligence product

> Some models merge Collection and Processing into one step (5-step version).

## Intelligence Sources

| Source | Description |
|---|---|
| **OSINT** | Open sources: forums, social media, passive recon, vulnerability/malware databases, public repositories (and some dark-web monitoring) |
| **Commercial Threat Intel** | Third-party vendors |
| **Vendor Reports & Research** | Published reports and whitepapers |
| **ISACs** (Information Sharing and Analysis Centers) | Organizations providing centralized cyber threat info sharing between private and public sectors |

# YARA

A tool for **identifying and classifying malware samples** based on textual or binary patterns. Each rule has a set of strings and a boolean condition.

```bash
yara rule.yar sample.exe -s      # print matching strings and their offsets
```

## Rule Structure

```yara
rule silent_banker : banker
{
    meta:
        description = "This is just an example"
        threat_level = 3
        in_the_wild = true

    strings:
        $a = {6A 40 68 00 30 00 00 6A 14 8D 91}
        $b = {8D 4D B0 2B C1 83 C0 27 99 6A 4E 59 F7 F9}
        $c = "UVODFRYSIHLNWPEJXQZAKCBGMT"

    condition:
        $a or $b or $c
}
```

## Example — Detect Mimikatz by URL String

> The string below is only an example. Confirm that a string really exists in your sample (e.g., with `strings`) before relying on it, and use `ascii wide` because Windows binaries often store text as UTF-16.

```yara
rule MAL_Mimikatz_WIN_EXE_Example
{
    meta:
        description = "Detects the Mimikatz executable using a hardcoded URL string"
        author      = "NIZARSEC"
        date        = "2025-08-12"
        reference   = "https://example.com/reference"
        tags        = "malware, windows, lsass"
        hash        = "<SHA256 of the analyzed sample>"
        version     = "1.0"

    strings:
        $URL          = "https://mimikatz.com" ascii wide
        $PE_Signature = { 4D 5A }    // "MZ" in hex

    condition:
        $PE_Signature at 0 and $URL
}
```

## Example — Using the PE Module

```yara
import "pe"

rule MAL_Mimikatz_WIN_EXE_Example_PE
{
    meta:
        description = "Detects the Mimikatz executable using a hardcoded URL string (PE module)"
        author      = "NIZARSEC"
        date        = "2025-08-12"
        reference   = "https://example.com/reference"
        tags        = "malware, windows, lsass"
        hash        = "<SHA256 of the analyzed sample>"
        version     = "1.0"

    strings:
        $URL = "https://mimikatz.com" ascii wide

    condition:
        pe.is_pe and $URL
}
```
